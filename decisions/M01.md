## Store preloved config in tenant_preloved_settings 1:1, not on tenants or workflow tenant_settings
- **ID:** 52798c05-e8e7-4979-8374-c5f5586f7334
- **Date:** 2026-09-06T14:03:44Z
- **Stage:** build:M01
- **Decision:** New table tenant_preloved_settings (PK tenant_id) with prelovedEnabled, intakeMode, priceFractionOfNew, holdDays, donatedGstFree, refuseList, unused commissionBps, timestamps.
- **Why:** tenant_settings is fulfilment/workflow. A separate row matches the spec option, keeps GST/refuse off that table, and lets M03 read settings without touching workflow helpers. Implemented as a new table, not columns on tenants.
- **Alternatives:** Add columns to tenant_settings; add columns to tenants.
- **Pros:** Clear domain split; existing getTenantSettings unchanged; cascade-delete with tenant.
- **Cons:** One extra table versus a wider tenant_settings row.
- **Risks / known issues:** New tenants may lack a row until first save — getPrelovedSettings returns in-code defaults. Migration backfills existing tenants only.
- **Links:** specs/milestones/M01-preloved-foundation.md

## Price fraction warns above 0.50, hard-bounds 0.01–2 after round-to-2dp, shared helper across Zod/upsert/UI
- **ID:** 8f116a7c-32dd-4517-b419-0395a50555dc
- **Date:** 2026-09-06T14:03:45Z
- **Stage:** build:M01
- **Decision:** Soft warning at > 0.50. roundPriceFractionOfNew + isPersistablePriceFractionOfNew own numeric(4,2) writes. Values that round to 0.00 are rejected. upsert throws RangeError if the helper is bypassed.
- **Why:** Spec 50% is a warning not a legal cap. z.number().gt(0) then toFixed(2) accepted 0.001 and stored 0.00. One helper prevents drift across three write paths.
- **Alternatives:** Clamp to 0.01; inline checks in each file; hard-cap at 0.50.
- **Pros:** Cannot persist 0.00; UI sends the rounded number the API stores; tenants can still save 51–200% of new.
- **Cons:** A direct helper call with a bad fraction surfaces as 500 from the PATCH catch-all.
- **Risks / known issues:** Existing 0.00 rows are not migrated; M03 intake should keep the same warn-and-save rule.
- **Links:** specs/milestones/M01-preloved-foundation.md

## upsertPrelovedSettings is a single insert().onConflictDoUpdate(); neon-http db.batch not needed for one row
- **ID:** 7c16c268-026e-439d-9d14-d62b667a4746
- **Date:** 2026-09-06T14:03:45Z
- **Stage:** build:M01
- **Decision:** Write only provided patch columns plus updatedAt on conflict. Table defaults cover omitted fields including intakeMode. No SELECT-merge and no db.batch.
- **Why:** neon-http has no interactive transactions; db.batch is for multi-statement writes. Wrapping one insert added types with no extra safety.
- **Alternatives:** SELECT-merge then batch; db.transaction (forbidden).
- **Pros:** Fewer round-trips; partial PATCH cannot clobber other columns.
- **Cons:** First insert of a partial patch uses DB defaults, not defaultPrelovedSettings(), for omitted fields.
- **Risks / known issues:** If code defaults and DB defaults drift, a first-time partial insert follows the DB.
- **Links:** specs/milestones/M01-preloved-foundation.md
