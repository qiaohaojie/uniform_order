## Accept SKU upsert and accepted event run in one db.batch via INSERT…SELECT
- **ID:** bbe4b22a-6654-4d1d-8947-a3dbd0fb562d
- **Date:** 2026-09-06T17:01:00Z
- **Stage:** build:M03
- **Decision:** acceptAndPool composes the ON CONFLICT SKU upsert and the accepted intake-event insert in one neon-http db.batch. The event is INSERT…SELECT of the eligible unique-key row, not a VALUES insert using the upsert RETURNING id.
- **Why:** neon-http has no interactive transactions. Sequential upsert then event insert can leave a qty increment if the event write fails, and a client retry would increment again. Batch queries are composed before INSERT…RETURNING is available, so a VALUES insert would still write an event when the conflict WHERE no-ops.
- **Alternatives:** Sequential writes; db.transaction (unsupported on neon-http); VALUES event insert from the upsert RETURNING id.
- **Pros:** A failed event cannot leave a qty increment that a retry would apply again; the event is skipped when the conflict WHERE no-ops.
- **Cons:** db.batch is a pipeline, not a true transaction; one statement can still succeed without the other.
- **Risks / known issues:** If the driver applies the upsert but drops the event, a retry may 409 on expired stock or double-count if WHERE still matches.
- **Links:** apps/web/src/db/preloved-queries.ts acceptAndPool; specs/milestones/M03-operator-intake.md (neon-http db.batch invariant)

## Refuse accept onto expired in-stock SKUs until write-off zeros qty
- **ID:** 7ef0c42e-223e-4049-8cbc-af87a910afab
- **Date:** 2026-09-06T17:01:00Z
- **Stage:** build:M03
- **Decision:** ON CONFLICT setWhere and the event SELECT both require qty_on_hand=0 OR expires_at IS NULL OR expires_at >= listedAt. Empty RETURNING throws PrelovedExpiredStockError and the intake API returns 409. Restock after qty 0 still restarts listedAt/expiresAt.
- **Why:** Mixing a fresh donated unit onto a hold that is already past would hide write-off-eligible stock and keep the old expiry. Spec write-off list is SKUs past holdDays; accept must not steal that qty. Unique pooled key including inactive rows forbids a second SKU.
- **Alternatives:** Allow increment and refresh listedAt; auto-write-off then restock in the same request; insert a second SKU (blocked by unique including inactive).
- **Pros:** Write-off list stays accurate; restock after qty 0 still works; unique pooled key preserved.
- **Cons:** Operator must write off before accepting the same item+size+condition while expired qty remains.
- **Risks / known issues:** Operators may read the 409 as a broken accept unless the intake UI surfaces the code.
- **Links:** apps/web/src/db/preloved-queries.ts canAcceptOntoSku; lib/preloved.ts PrelovedExpiredStockError; POST /api/tenant/:tenantId/preloved/intake

## Write-off records preloved_intake_events written_off only; no audit_events row
- **ID:** 349ef46e-a465-4ae4-98be-28bd9d753a62
- **Date:** 2026-09-06T17:01:00Z
- **Stage:** build:M03
- **Decision:** writeOffPrelovedSku zeros qty_on_hand and inserts preloved_intake_events action=written_off. It does not insert audit_events. Retry of an already-zero listing inserts the missing event instead of 409.
- **Why:** M01 already made intake events the intake+write-off audit table (3b96a603). Spec says audit/intake event. Dual-writing audit_events would need a target_type change and duplicate the same fact. Donation-only write-off has no parent payout to log there.
- **Alternatives:** Also insert audit_events; write-off-only in audit_events; a separate write-off table.
- **Pros:** One table for accept/reject/write-off; retry can find written_off by listing; no target_type migration.
- **Cons:** The existing tenant activity feed (audit_events) will not show write-offs.
- **Risks / known issues:** Operators looking at the operator audit log will miss write-offs until a later feed is added.
- **Links:** apps/web/src/db/preloved-queries.ts writeOffPrelovedSku; POST /api/tenant/:tenantId/preloved/skus/:skuId/write-off; decisions/M01.md 3b96a603; lib/audit/log.ts unused by M03

## drizzle insert().select() for intake events must list every table column in schema order
- **ID:** 4e507191-a2e7-494f-b8f7-1ee3ef113336
- **Date:** 2026-09-06T17:33:18Z
- **Stage:** build:M03
- **Decision:** acceptAndPool's INSERT…SELECT of preloved_intake_events includes id, rejectReason, and createdAt in the same order as schema.ts. Persist-time Playwright failed with 'selected fields are not the same or are in a different order compared to the table definition' until those columns were added.
- **Why:** Drizzle 0.45 compares the select object to the full table definition, including columns that have SQL defaults. Omitting id/createdAt/rejectReason 500s the accept path.
- **Alternatives:** Use insert().values() after the upsert RETURNING (not composable in the same db.batch); raw SQL CTE.
- **Pros:** Keeps SKU upsert + event in one db.batch; accept path now proven by Playwright.
- **Cons:** Select object must be updated whenever intake event columns change.
- **Risks / known issues:** A later schema column will 500 accepts until the select list is extended.
- **Links:** specs/milestones/M03-operator-intake.md
